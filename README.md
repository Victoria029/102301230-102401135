# 校园失物招领

> 福州大学 2026 秋软件工程 · 结对作业（第二次之程序实现）
>
> 结对成员：102401135 何慧渊 ｜ 102301230 林为峰

把第一次结对作业用墨刀做的原型（首页 / 搜索结果 / 信息详情 / 发布信息 / 发布成功 / 个人中心）做成一个**真的能跑的程序**，并补上原型里最有价值的那个原创点：**认领验证（防冒领）**。

核心闭环：**发布信息 → 浏览 / 搜索 → 查看详情 → 联系发布者 → 更新状态**

---

## 一、怎么跑起来

**不需要装任何东西**：不用 Node、不用 npm、不用起服务器、不用联网。

1. 把整个 `campus-lost-found` 文件夹下载到本地（`git clone` 或 `Code → Download ZIP`）；
2. **用谷歌浏览器 Chrome 双击打开根目录下的 `index.html`**；
3. 第一次打开会自动灌入一批演示数据（其中 3 条归属于"你本人"），首页立刻有内容。

运行单元测试：双击 **`test/test.html`**，Chrome 打开后会自动跑完并在页面上给出报告。

> **请务必用 Chrome。** 本项目用 `localStorage` 存数据。不同浏览器对 `file://` 协议下本地存储的处理不一样，Chrome 把所有本地文件视为同一来源，页面之间能共享数据；换成其他浏览器可能出现"发布成功后跳到成功页，数据却读不到"的情况。

| 12 | 进「我的」→ 人工审核 | 看到种子数据里那条待处理申诉（含对方写的细节与联系方式）；点「同意交还」→ 生成线下交接编号 |
| 13 | 「我的」→ 我的发布 → 点「标记已归还」 | 条目移到「已完成」，首页上它变灰并沉到后面 |
| 14 | 点「＋ 发布信息」，类型选「招领」、分类选「雨伞雨具」 | 出现**出题区**，可从下拉框插入分类模板，能加判断题 / 选择题、增删选项、指定正确答案 |
| 15 | 同一页把分类改成「其他」 | 出题区换成一段**信任模式说明**（讲清为什么不出题、代价是什么）；再切回「雨伞雨具」，**之前写的题会被放回来** |
| 16 | 发布成功页 | 显示信息编号，并给出「可能相关的信息」（类型相反 + 同类 + 标题有两字重合，最多 3 条） |

**想恢复初始状态**：「我的 → 本地数据 → 恢复演示数据」。

### 命名约定

| 对象 | 约定 | 例子 |

## 三、功能清单

### 作业要求的主线

| 功能 | 说明 |
| --- | --- |
| 浏览信息 | 首页卡片列表，支持类型 / 分类 / 地点 / 状态四维自由组合筛选，每项实时显示条数 |
| 发布寻物 / 招领 | 一套表单两种类型；必填与长度校验、联系方式格式校验、日期不允许填未来 |
| 搜索物品 | 关键词命中标题、描述、地点、分类名、类型名，多词按「与」；命中词高亮 |
| 查看详情 | 完整描述、分类、地点、日期、发布时间、浏览量 |
| 联系发布者 | 一键复制联系方式；`file://` 下 Clipboard API 不可用时降级为手动复制框 |
| 更新状态 | 发布者标记「已找到 / 已归还」，可恢复为进行中；已完成信息置灰沉底 |
| 个人中心 | 个人资料（发布时自动带出）、发布统计、我的发布管理 |

### 附加特点

| 功能 | 解决什么问题 |
| --- | --- |
| **认领验证（防冒领）** | 招领信息由拾得者出 3~5 道客观题，认领人**一次答完全部题目、全部答对**才解锁联系方式。详情页展示联系方式这件事，从"口头约定"变成"程序判断" |
| **限制 3 次 + 统一判定** | 未通过时只回「回答的细节与描述不符」，**不告诉是哪一题错**——否则每错一次就排除一个选项，3 次机会足够把答案试出来 |
| **申诉（人工审核）** | 3 次用完后解锁申诉通道：认领人写下"只有物主才知道的细节"和联系方式，发布者在「我的发布 → 人工审核」逐条处理，同意则生成线下交接编号 |
| **「其他」类走信任模式** | 这类物品没有能锁死的特征，硬出题只会逼人把描述抄一遍，所以不设验证题、联系方式直接公开，并把"代价"写在页面上 |
| **一键复制联系方式** | 校园场景是"复制号码 → 打开微信"，省掉手抄和误记；复制失败时弹出可手动复制的输入框，事情还办得成 |
| **物品分类 + 校园地点筛选** | 人是按场景找东西的（"我今天在图书馆丢的"），不想先想关键词；选项右侧实时显示条数 |
| **智能配对提醒** | 不做聊天、不做地图，就用这一步把"丢的人"和"捡的人"第一次关联起来：类型相反 + 分类相同 + 标题有两字重合，最多 3 条 |
| **搜索历史 + 热门搜索** | 找东西往往是反复搜的；热门词由真实数据统计得出，不写死 |
| **发布草稿自动保存** | 填一半误关页面是真实会发生的；回来时问一句"要恢复吗"，而不是默默填回去或默默丢掉 |
| **照片上传 + 本地压缩** | 直接存手机原图会顶到 localStorage 配额，压缩到最长边 480px / JPEG 0.72 后再存 |
| **数据导出 / 导入 / 恢复演示数据** | 没有后端，所以把"数据到底存在哪、能存多久"写在明面上，并给出迁移手段 |
| **响应式** | 同一套 HTML：宽屏是网页版（顶部导航 + 左侧筛选栏 + 卡片网格），窄屏自动变手机版（底部 Tab 栏） |

## 四、单元测试

**工具：Mocha 10.8.2 + Chai 4.5.0（浏览器构建，随仓库提交）。**

- **入口**：双击 `test/test.html`，Chrome 自动跑完；跑完会往 `<html>` 上写 `data-selftest="PASS|passing=53|failing=0"`，方便命令行检查。
- **为什么不用 `npm install mocha`**：本项目本身不需要 Node。为了跑测试先让助教装一整套依赖，就违背了"下载后双击就能用"这条底线。所以把两个库的浏览器构建直接提交进仓库，`test.html` 用 `<script>` 标签按顺序加载，离线可用。
- **一个版本上的坑**：Chai 从 5.x 起只提供 ES Module，用普通 `<script>` 加载会报 `SyntaxError: Unexpected token 'export'`，而 `file://` 下又不能用 `type="module"`（会被 CORS 拦）。所以 Chai 固定在 **4.5.0** —— 最后一个带 UMD 浏览器构建的版本。

### 构造测试数据的思路

1. **等价类划分 + 边界值**：每个长度类字段同时测边界内侧和越界一侧。物品名称限 2~40 字，就测 1 字（拒）、2 字（过）、40 字（过）、41 字（拒）。
2. **每次只动一个变量**：`fixtures.js` 里有一份"必然合法"的基准数据，每条用例只改其中一个字段。这样一旦失败，出错原因就是唯一的那个。
3. **正例反例成对写**：只测"应该通过"会写出过宽的实现，只测"应该拒绝"会写出过严的实现。搜索、答案比对、权限校验这三处全部成对写。
4. **把不确定性消灭掉**：时间注入固定成 `2026-10-09T10:00:00`；需要验证排序时用一个**可推进的时钟函数**（`T.makeClockStore()`），因为时间不动的话所有 `createdAt` 相等，"最新在前 / 最早在前"根本没被验证到。涉及"3 次失败后锁定"的用例就老老实实失败三次，而不是想办法"快进"。
5. **每个用例一个干净仓库**：注入 `LF.createMemoryAdapter()`，用例之间互不污染。

### 我们假想的"刁难测试人员"会怎么挑刺

| 刁难思路 | 应对（对应用例） |
| --- | --- |
| 前端藏起来了，数据里还在吧？ | 断言 `JSON.stringify(view)` 里搜不到 `answer`；断言 `claims` / `appeals` 根本不在公开对象里 |
| 从返回值里能看出哪题错了吗？ | 断言"全错"与"只错一题"的返回对象**序列化后完全一致**，连题号都不出现 |
| 次数没用完就想过申诉？ | 断言 `attemptsLeft > 0` 时 `submitAppeal` 被拒，并提示"还剩几次" |
| 一次不选完就提交？ | 断言返回"还有 N 道题没作答"，且 `attemptsLeft` **不变** |
| 前端传了 id、浏览量，能覆盖原值吗？ | 恶意构造 `update(id, {id:'伪造', views:9999, ownerId:'黑客', status:'done'})`，断言这些字段不被篡改 |
| 别人能不能改我的信息？ | 用另一个 actor 调 `markDone` / `updatePost` / `removePost` / `listAppeals` / `resolveAppeal`，断言全部被拒 |
| 存储里塞坏数据会白屏吗？ | 写入非法 JSON、非数组、混入 `null` 与字符串、缺字段的对象，断言仍能正常工作 |
| 存储写满会怎样？ | 用会抛 `QuotaExceededError` 的假适配器，断言返回**中文可操作提示**且内存里不留脏记录 |
| 搜索框输入 `(` 会不会崩？ | 用 `indexOf` 而不是 `RegExp`，天然免疫（有用例钉住） |
| 空关键词、纯空格、全角空格？ | 断言返回全部，而不是返回空列表 |
| 旧版本的数据打开会不会崩？ | 造一份第一次结对作业那份脚手架的数据，断言能迁移过来并正常操作 |
| 换过题目之后老认领人怎么办？ | 断言换题后 `attemptsLeft` 重置为 3、旧认领记录清空 |

## 五、已知限制（如实写出来，而不是藏在代码注释里）

1. **没有后端，数据只在本机。** 换设备、换浏览器、清除浏览器数据都会看不到这些内容。这是"下载后双击就能用"这一约束带来的必然结果，所以提供了导出 / 导入作为补偿。
2. **认领次数记在"信息"上，而不是按认领人区分。** 同一条信息被答满 3 次之后，后面来的人也只能走申诉通道。真实环境应该把尝试次数按人区分并存到服务端。
3. **申诉通过后的解锁状态记录在本机。** 因为认领人和发布者在本项目里共用同一份 localStorage，"发布者同意交还"之后解锁的是这台设备上的访问权限。真实环境需要服务端按认领人下发。
4. **发布者身份靠本机标识，不是账号。** 首次打开生成一个随机 `ownerId` 存在本地，用来判断"哪些信息是我发的"。换设备后原来的信息就不再属于"我"了。
5. **`file://` 下的剪贴板能力受限。** `navigator.clipboard` 在非安全上下文常常拿不到，已做 `execCommand` 降级 + 手动复制兜底，但这一层依赖浏览器实现。
6. **没有做真实浏览器的自动化端到端回归。** 交付的自动化测试是数据层 + 页面静态一致性；页面的视觉与交互仍依赖人工走查（开发过程中我们另外用 headless Chrome 做过一轮页面与交互检查，但那部分脚本没有随仓库提交，因为它依赖本机安装的 Chrome）。

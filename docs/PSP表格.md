## 任务拆解的依据

上表的阶段划分直接对着本次实际做出来的东西，不是凭空估的：

| 阶段 | 对应到本仓库的哪些具体工作 |
| --- | --- |
| Analysis | 读第一次作业的原型与需求、确定"不做后台 / 实名 / 聊天 / 地图"的边界、决定加认领验证 |
| Design Spec | 写 `docs/设计文档.md`：分层方案、数据模型、四个必须做对的规则 |
| Design | 页面清单与路由、`config.js` 业务字典、题目数据结构、存储降级链 |
| Coding | `store.js`（业务规则）+ 9 个页面控制器 + 3 个 CSS + 9 个 HTML |
| Code Review | 互查：对方写的模块自己走一遍，检查"界面上藏了、但数据层没拦"这类问题 |
| Test | 53 个用例的编写与调试、浏览器里的渲染与交互走查 |
| Reporting | README、目录说明、流程图、博客 |

## 偏差分析（待填完实际耗时后补写）

下面是**写法示例**，说明这一栏该怎么写才有意义 —— 不要只写"比预估多 30 分钟"，要写清"多在哪、为什么、下次怎么改"：

> 超出预估最多的是 **Coding**：一是"看起来很简单"的交互其实很费时间，比如题目编辑器里"改文字不重绘、改结构才重绘"这条规则的调试；二是搜索的边界情况（全角、零宽字符、正则元字符）反复补了几轮。
>
> **Analysis** 超时的原因是中途调整了一次范围：最初想过把"认领验证"做得更复杂（按分类填特征、手打答案），讨论后发现它在判定准确性和防试探上都不成立，整块推翻重做成客观题，这一轮返工算在了 Analysis 和 Design 里。
>
> **Test** 超时主要是补边界用例：写完才发现"空选项行要不要重排答案下标""全错与只错一题返回结构是否一致"这类地方必须钉住，否则改一次就可能悄悄退化。
>
> **下次改进**：把"交互走查"单独列成一个任务并预留时间，而不是算在 Coding 里；先写一版能跑的最小骨架，再往上加附加特点，避免返工。

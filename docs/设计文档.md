## 一、需求回顾与范围界定

第一次结对作业已经明确：本次**不要求**复杂后台管理、实名认证、即时聊天、地图定位。所以实现时直接砍掉这些方向，把精力集中在题目点名的核心闭环上：

> **发布信息 → 浏览 / 搜索 → 查看详情 → 联系发布者 → 更新状态**

设计过程中，我们重点回答了两个问题（这两个问题不写代码是回答不清楚的）：

### 问题一：联系之后，这条信息怎么结束？

**回答**：由**发布者**在详情页或「我的发布」里标记为「已找到 / 已归还」。标记后：

- 信息在列表中**置灰并沉到后面**（不让已完结的信息淹没活跃信息）；
- 详情页**不再展示联系入口**，并提示"请勿再打扰发布者"——从机制上减少无效联系；
- 支持「恢复为进行中」以防误标；
- 标记是**幂等**的：重复点不会改动原有的完成时间（否则"已归还于昨天"会变成"已归还于刚才"，记录就不准了）。

### 问题二：没有登录系统，怎么知道谁是发布者？

**回答**：采用**本机发布者标识**。首次打开时生成一个随机 `ownerId` 存进本地数据，「我的发布」只展示标识匹配的信息；状态维护、编辑、删除、查看申诉明细都要在这个标识上做归属校验。

**关键的一条纪律**：归属校验必须放在**数据层**，不能靠"界面上不显示按钮"。因为前端隐藏只是让人点不到，绕过界面直接调数据层一样能改。所以 `markDone / updatePost / removePost / listAppeals / resolveAppeal` 每一个都在数据层里判 `post.ownerId !== actor` 就直接拒绝。

### 问题三（原型里没想清楚、实现时才逼出来的）：招领信息的联系方式，到底给谁看？

这是我们在实现过程中撞上的、原型阶段没考虑到的问题，也是本项目附加特点的起点：

- **全公开** → 任何人都能看到，**冒领几乎没有成本**。真失主还没看到消息，东西可能就被别人领走了；
- **完全不公开** → 失主联系不上拾得者，信息等于白挂。

这是个两难。我们的解法是引入一个**只有物主能通过的门槛**：拾到东西的人出几道只有物主答得对的客观题，认领人全部答对才解锁联系方式。详见第五节。

## 二、技术选型

| 选项 | 结论 | 理由 |
| --- | --- | --- |
| 形态 | Web（Chrome 直接打开 HTML） | 与原型一致；测试成本最低 |
| 框架 | **不用框架，原生 HTML / CSS / JS** | 作业要求"下载所有文件后用谷歌浏览器运行 html 就能展现预期结果"。引入构建工具或框架反而增加了环境要求，也让助教多一步 `npm install` |
| 数据持久化 | `localStorage`（无后端），不可用时降级 | 单机演示足够；见第六节的降级链 |
| 页面组织 | **多页应用**（9 个 HTML），不是单页路由 | 页面数量与原型一一对应；`file://` 下多页比 hash 路由更直观，也便于助教"点开某一页直接看" |
| 脚本 | 普通 `<script>`，无 `import` / `export` | `file://` 下 ES Module 会被 CORS 拦掉 |
| 单元测试 | **Mocha 10.8.2 + Chai 4.5.0**（浏览器构建随仓库提交） | 双击 `test/test.html` 即跑，不装 Node、不起服务器、不联网 |

## 三、架构分层

```
        页面 HTML（只管结构）
              ↓
        page-*.js（收集输入、调数据层、渲染结果）
              ↓
   ┌──────────────────────────────────────┐
   │  store.js  ★  全部业务规则            │
   │  校验 / 增删改查 / 搜索筛选排序 /      │
   │  状态流转 / 认领验证 / 申诉 / 迁移     │
   └──────────────────────────────────────┘
              ↓
   config.js（业务字典）  utils.js（纯函数）
              ↓
        存储适配器（localStorage → sessionStorage → 内存）
```

**为什么要分这一层**：这几件事必须做对，做错了后果严重——

1. 验证题的正确答案不能泄露（这是防冒领的根基）；
2. 状态流转不能乱（东西还回去了，信息还挂着"待认领"，别人就会白跑一趟）；
3. 只有发布者能改自己的信息；
4. 搜索得搜得到（搜"校园卡"找不到"校园卡一张（学号 2023****）"，用户就不用第二次了）。

这四件事全是"输入 → 输出"的逻辑，跟界面长什么样没关系。把它们全部收进 `store.js` 之后，有两个直接好处：

- **改一处规则就全局生效**，不会出现"详情页改了、搜索结果还漏着"；
- **这些规则能被单元测试一条条钉住，而且不需要浏览器环境**。

实现上最关键的一步是**存储注入**：`createStore(storage)` 只要求传进来的对象有 `getItem / setItem / removeItem` 三个方法（和 `localStorage` 一模一样），于是：

| 运行环境 | 注入的东西 | 结果 |
| --- | --- | --- |
| 浏览器 | `LF.createBrowserAdapter()` | 数据落盘，刷新还在 |
| 单元测试 | `LF.createMemoryAdapter()` | 每个用例一个干净仓库，互不干扰 |

同一份业务代码，一个字都不用改。测试因此不需要 jsdom、不需要起服务器、不需要装 Node。

## 四、数据模型

一条信息的核心字段（内部结构，落盘时的形态）：

```js
{
  id: 'p_xxx',                 // 内部主键
  code: 'LF20261009001',       // 展示用编号，线下核对时报这个
  type: 'lost' | 'found',      // 寻物 / 招领
  title, category, location, happenedAt, description,
  contactName, contactWay,     // 联系方式
  photo,                       // 压缩后的 dataURL
  status: 'active' | 'done',
  doneType: 'found' | 'returned' | null,
  doneAt, createdAt, updatedAt, views,
  ownerId,                     // 本机发布者标识

  questions: [                 // ★ answer 永远不出现在对外的对象里
    { id, type: 'judge' | 'choice', stem, options: [...], answer: 0 }
  ],
  attemptsLeft: 2,             // 剩余作答次数
  claims: [                    // 收到的认领记录（只有发布者能看）
    { at, passed, voucher }
  ],
  appeals: [                   // 人工审核申请（明细只有发布者能看）
    { id, claimantName, contact, detail,
      decision: 'pending' | 'accepted' | 'rejected', note, voucher, createdAt, decidedAt }
  ]
}
```

整个库存在**一个**键 `lf_db_v1` 下（`{version, seq, ownerId, posts, profile, history, draft, unlocked, vouchers}`）。选单键而不是分键，是因为写一次就是一个原子操作，迁移和"清空/导出"都只需要处理一个对象。

## 五、核心机制：认领验证（防冒领）

### 5.1 要解决的问题

招领信息如果把联系方式直接公开，任何人都能看到，真正的主人反而可能被抢先联系；但完全不给联系方式，又没法线下交接。

### 5.2 我们的方案

**拾得者出 3~5 道客观题（判断题 / 选择题），认领人一次答完全部题目，全部答对才解锁联系方式；最多答 3 次；3 次全败转入人工审核。**

四个设计决定，每一个都是被一个具体问题逼出来的：

| 决定 | 被什么问题逼出来的 |
| --- | --- |
| **只允许判断题和选择题** | 手打答案会带来"深蓝 / 藏青""蓝色小熊贴纸 / 小熊贴纸"这类措辞歧义，真失主反而被判错。判定从"文本比对"换成"选项下标比对"之后，这一整类误判直接消失 |
| **一次性答完全部题目，不分页** | 分页会让人以为可以回头改，也会让人误以为系统在逐题判定——而逐题反馈正是我们要避免的 |
| **只回「通过 / 不通过」，不告诉哪题错** | 如果告诉认领人错在哪一题，每答错一次就能排除一个选项，3 次机会足够把答案试出来，限制次数形同虚设 |
| **未答完提交不消耗次数** | 否则用户会被自己的手滑消耗掉机会——这是我们能替他挡住的 |

### 5.3 什么时候**不该**出题

把"锁定特征 + 出题验证"推到底，会撞到两个边界：

**① 寻物信息不出题。** 寻物的人本来就希望别人联系他，给他设门槛是反的。所以验证只加在**招领**这一侧——门槛只设在需要门槛的那一侧。

**② 「其他」类不出题。** 这一类之所以是「其他」，正是因为物品没有客观、能锁死的细节（一本书、一串钥匙、一个说不清型号的充电器）。对它做一个自问：**这一类该出什么题？** 答案是出题人只能把描述里的细节再抄一遍（"扉页上写着谁的名字"配上描述里的"扉页有名字"），同一份信息写两次，而冒领者照着公开描述就能选对——**在一类根本没有可锁特征的信息上强制出题，只会逼人编题。**

所以这一类改成**对照组**，走**信任原则**：不设验证题，描述、照片和联系方式直接公开。并且把**代价**写在页面上：

> 这一类没有防冒领闸门，理论上谁先看到都能联系你。所以**别把唯一凭据写进公开描述**（比如"书里夹着一张写名字的借书凭条"——这句话本身就是答案）。

判断逻辑收在一个函数里，依据是"这个分类在字典里有没有公开特征定义"，而不是手写 `category === 'other'`：

```js
LF.allowVerifyFor = function (categoryKey) {
  var c = LF.categoryOf(categoryKey);
  if (!c) return null;          // 三态：分类压根不在字典里，无从判断
  return !!c.allowVerify;       // true = 必须出题；false = 明确不出题
};
```

返回**三态**而不是布尔，是为了脏数据：分类不在字典里时，校验应当跳过出题这一条，免得在"分类错误"之上再叠一条用户改不掉、也无从理解的"请至少出 3 道验证题"。

### 5.4 出题结构由数据层兜底

题目结构不靠界面保证：

- 判断题的选项**固定**为「正确 / 错误」，发布者传什么都不算数；
- 选择题里的空选项行会被丢掉，**正确答案下标跟着重排**。

```js
// 空选项行被丢掉后，原来指向第 3 项的答案要落到第 2 项上
LF.normalizeQuestions([{ type:'choice', stem:'伞骨有几根',
                         options:['6 根','','8 根'], answer:2 }]);
// → options: ['6 根','8 根'], answer: 1
```

**为什么由数据层重排下标**：界面上"删除一个选项""切换题型"都会改动选项数组，如果直接在页面上算正确答案的下标，很容易出现"看着选的是第 2 项，存进去却指到第 3 项"。把重排规则放在数据层并配单元测试，这类错位就只有一个地方可能出错。

另外，新增题目时**不预选正确答案**。默认勾上"正确"能让发布者少点一下，但也可能就这么发出去了——而一个错的答案是直接把真失主锁在门外，代价比多点一下大得多。

### 5.5 判定与解锁流程

```
发布者出题(3~5)  ──→  招领信息带上 questions
                          │
        认领人打开详情 ────┤ needsVerify? ──否──→ 联系方式直接可见
                          │ 是
                          ↓
                  锁定：只显示"通过认领验证后可见"
                          │
                  点「开始认领验证」→ startClaim() 下发题目（无 answer）
                          │
                  一次选完全部题目 → submitClaim(answers)
                          │
        ┌─────────────────┴──────────────────┐
   未答完                               已答完
   「还差 N 题」                     全部答对? ──是──→ 解锁 + 生成凭证码 CL-YYYY-XXXX
   不扣次数                                │
                                     否 → 扣一次次数
                                          只回「回答的细节与描述不符」
                                          │
                                  attemptsLeft == 0 ?
                                          │ 是
                                   解锁申诉（人工审核）
```

### 5.6 申诉：一次真正落库的表单

3 次用完后，认领人可以写下"只有物主才知道的细节"+ 称呼 + 联系方式，由发布者在「我的发布 → 人工审核」里逐条处理：**同意交还**则解锁联系方式并生成线下交接编号；**驳回**则要求写一句理由，这句话会回给申诉人。

**为什么不做成一个"请线下联系发布者"的弹窗**：弹窗只是把问题推回给用户，发布者手里没有任何可判断的凭据。表单则把判断依据存进这条信息，发布者才有得看。

页面上还刻意先摆一道"提问"：答完 3 次都没过，最常见的原因其实是这件东西本来就不是你的。所以在让他填表之前，先请他自问一句，并说明"占用别人的时间，也会让真正需要的人排在后面"。

## 六、几处值得单独说明的实现

### 6.1 `toPublic()` —— 防冒领的第一道闸门

对外返回的每一个对象都经过这一层处理：

```js
out.questions = …            // 只给题干和选项，answer 在这一步被剥掉
out.contactWay = locked ? '' : post.contactWay;   // 未解锁时联系方式根本不进页面
out.contactName = isOwner ? post.contactName : LF.maskName(post.contactName);  // 张**
out.claimCount = isOwner ? post.claims.length : 0;   // 非发布者连"有多少人试过"都不透露
// claims / appeals 一个字段都不带出去
```

**这里是"删掉"而不是"界面上不显示"。** 区别很关键：如果只是前端 `display:none`，答案、认领记录、申诉人的联系方式仍然在内存对象里，打开控制台就能看到。**把它们从数据里删掉，才是真的拿不到。**

这几条规则有专门的测试直接验证（`test/specs/privacy.spec.js`）：拿到公开视图后断言题目对象没有 `answer` 属性、整个 JSON 序列化结果里搜不到 `answer` 字样、`claims` / `appeals` 两个键**压根不存在**。断言的是"数据里没有"，不是"界面没显示"——这样哪天有人为了"提升体验"把它加回来，用例会立刻变红。

### 6.2 统一判定：把"哪题错了"彻底留在数据层

```js
if (!passed) {
  return { ok: true, passed: false, remaining: left - 1,
           locked: left - 1 <= 0, canAppeal: left - 1 <= 0,
           message: '回答的细节与描述不符' };   // ★ 没有 failed / 没有题号
}
```

记录里**确实带了每题的对错**，但它只从 `debugState()` 出来给测试用；发布者看的是自己的信息，本来就知道答案，不需要这个字段。认领人拿到的失败结果里连题号都不出现。

**测试怎么钉住这条设计决策**：让同一个发布者的信息分别"只错一题"和"全错"，然后断言两个返回对象**序列化后完全一致**。这样将来谁为了"提升体验"把错题信息加回去，用例会立刻变红。

### 6.3 搜索：一个纯函数 + 一条容易踩的边界

```js
// 多词按「与」；命中范围包含分类名和类型名，所以搜"证件卡片"能找到标题写"校园卡"的信息
var terms = LF.normalizeText(keyword).split(' ').filter(Boolean);
var haystack = LF.normalizeText([title, description, location, 分类名, 区域名, 类型名,
  LF.maskName(contactName)].join(' '));
return terms.every(t => haystack.indexOf(t) !== -1);
```

三个考虑：

- **用 `indexOf` 而不是 `new RegExp`**：用户输入什么就搜什么，如果拼进正则解析，输入一个 `(` 就会让整个页面崩掉。
- **归一化里加了 NFKC 和零宽字符过滤**：从微信、QQ 复制过来的文字经常夹着看不见的零宽字符，人眼看着一样，字符串比较却不相等。
- **归一化和清理是两个函数**：`normalizeText()` 只用于**比较**，`clean()` 才用于**保存**。早先把两者混在一个函数里，"存的时候顺手做了全角转半角"，用户回看自己的描述发现字符被改了。所以刻意拆开，各自只服务一个目的。

### 6.4 分面统计：统计某一维时要忽略该维自身的筛选

筛选按钮右侧要显示"这个选项下有几条"。如果拿当前全部筛选条件去算，会出现一个尴尬的结果：**选中"图书馆"之后，其他地点的条数全变成 0，用户就没法从"图书馆"直接切到"食堂"了。**

所以 `facets()` 在统计某一维时，会从条件里剔除这一维：

```js
for (var d = 0; d < FILTER_DIMS.length; d++) {
  var ignore = {}; ignore[FILTER_DIMS[d]] = true;
  // 用 (opts - 这一维) 去统计这一维的各选项条数
}
```

### 6.5 存储降级链

`LF.createBrowserAdapter()` 按 **localStorage → sessionStorage → 内存** 的顺序探测并降级，每一步都**真写一次再删掉**来确认可用（`probeStorage()`）——因为无痕模式或企业策略下，连读 `localStorage` 属性都可能抛异常，"能拿到对象"不等于"能用"。

**为什么中间要夹一层 sessionStorage**：这是个多页应用，每跳一次页面，内存里的变量全部重置。如果 localStorage 不可用就直接退回内存，「发布 → 跳成功页」这一步数据就没了，主流程当场断掉。sessionStorage 至少能让同一标签页内把流程走完——**降级的目标是"功能仍然可用"，不是"程序不崩"这么低的标准。**

页面顶部会同步出现一条提示条，明确告诉用户当前数据的保留范围，而不是让他在毫不知情的情况下丢数据。

### 6.6 老数据必须能就地升级

`DATA_VERSION` 与 `migrate()`：改数据结构时版本号 +1，迁移里补一条分支。这不只是"补字段"，还要**清理已经不该生效的数据**。

具体到本项目：曾经给「其他」类挂过验证题的历史记录，在改成"这一类不出题"之后必须把题目清掉——否则发布者会被锁在一个**详情页还在要求答题、发布页却已经没有出题入口**的旧流程里，他连"把这套题删掉"都做不到。测试里专门造了这样一条老数据来钉住这个行为。

另外还实现了对**第一次结对作业那份脚手架**（存储键 `lost_found_list`，字段是 `name / place / desc / contact / createTime`）的一次性迁移，这样如果本机之前玩过旧版本，数据不会白丢。

**改规则时要同时问一句"老数据怎么办"** —— 用户看得见现象、却没有任何入口能修的状态，比报错更难被发现，因为它一切"正常"。

### 6.7 换题目 → 重新给满次数

发布者改了验证题之后，`attemptsLeft` 重置为 `MAX_ATTEMPTS`，旧的认领记录一并清空。否则老认领人会被上一版题目的失败记录卡住——他面对的是一道新题，却只剩下旧题消耗掉的机会。

### 6.8 发布页的两个交互细节

**① 题目编辑器不整块重绘。** 题干和选项都是输入框，如果每敲一个字就把整个表单重建一遍，焦点会丢，表现为"打一个字就跳出输入框"。所以分成两条路：

- 改文字（题干 / 选项内容）→ **只更新内存里的模型**，不重绘；
- 改结构（加题 / 删题 / 换题型 / 加删选项）→ 才重绘**那一道题**。

**② 切分类时把题目收起来，而不是丢掉。** 用户写三道题是花了心思的，只因为点错一下分类就被清空、切回来还得重写，那是我们在惩罚他的误操作。所以收进 `state.stashedQuestions`，切回需要出题的分类时再还给他，并提示一句"已把你之前写的验证题放回来"。

### 6.9 选项清晰度提醒：只提示、不拦截

有些出题方式会让真失主选错，比如把选项写成「深蓝色 / 藏青色」——同一种颜色的两种说法，东西其实是藏青色的同学看见「深蓝色」觉得说的就是自己，随手选了，答错一次，还被判成"细节与描述不符"。

所以我们做了一份**易混词组表**，把「深蓝 / 深蓝色 / 藏青 / 藏蓝色 / 靛蓝」归成一组、「浅蓝 / 淡蓝 / 天蓝 / 湖蓝」归成另一组，组内互斥、组间放行（"深蓝 / 浅蓝"能分清，不该拦）。判定时**取命中的最长那个词**——「浅蓝色」同时含「蓝色」和「浅蓝色」，不比长度就会归错组，把深蓝和浅蓝判成同一色。

**但这条规则只提示、不参与"能不能发布"的判定。** 理由是它一定会误报，而**误报多了，这条规则就会被当成噪音直接忽略掉——比不拦还糟**。页面上是边打字边提示，发布者自己决定改不改。

### 6.10 响应式：一套 HTML 服务两种形态

- 宽屏（≥900px）：桌面网页版——顶部导航 + 左侧吸顶筛选栏 + 两列卡片网格；
- 窄屏（<900px）：手机版——底部 Tab 栏 + 单列卡片 + 横向滑动的筛选条。

只用一个断点，避免中间态出现"两边都不像"的布局。筛选区**只有一份 DOM**，靠 CSS 在两种形态间切换——写两份 HTML 就一定会不同步（改了一边忘了另一边）。

## 七、测试策略

| 层次 | 做什么 | 覆盖 |
| --- | --- | --- |
| 单元测试 | 数据层全部业务规则，**浏览器内双击即跑** | 53 个用例 / 10 组 |
| 静态一致性 | 页面 JS 用到的 `id` 在 HTML 里是否存在、脚本与样式路径是否有效、页面互链是否 404 | 9 个页面 |
| 渲染检查 | 把每个页面真的在 Chrome 里跑一遍，检查关键内容是否渲染出来 | 9 个页面 + 5 个异常入口 |
| 交互流程 | 模拟点击 / 输入 / 提交，走通主流程与认领验证、申诉、状态维护 | 39 项断言 |

后三层是开发过程中另外做的（脚本依赖本机 Chrome，没有随仓库提交），但它们各补了一个盲区：

- 逻辑单测证明数据层对，**证明不了页面把它接对了**；
- 渲染检查证明页面能画出来，**证明不了按钮点下去真的有用**；
- 静态检查证明 `id` 对得上，**证明不了元素真的可见可点**。

**构造测试数据的思路**（详见 README 第四节）：等价类划分 + 边界值、每次只动一个变量、正例反例成对写、把不确定性（时间）消灭掉、每个用例一个干净的内存仓库。

## 八、已知限制

1. 没有后端，数据只在本机；换设备 / 清缓存即失。已提供导出 / 导入补偿。
2. 认领次数记在"信息"上而不是按认领人区分——这条信息被答满 3 次后，后面来的人也只能走申诉。真实环境应把尝试次数按人区分并存到服务端。
3. 申诉通过后的解锁状态记录在本机（因为认领人与发布者共用同一份 localStorage）。
4. 发布者身份靠本机随机标识，不是账号。
5. `file://` 下剪贴板能力受限，已做降级 + 手动复制兜底，但这一层依赖浏览器实现。
6. 没有做真实浏览器的自动化端到端回归纳入仓库（见第七节说明）。
